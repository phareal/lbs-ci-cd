CI/CD DevOps pour une User API

Node.js · Express · SQLite · Jest · GitHub Actions · AWS EC2

Roland NOUAHO · 2026

Objectifs de la démo

  • Montrer un pipeline CI/CD complet autour d’une API Node.js
  • Mettre en avant les garde-fous qualité (lint + tests + coverage)
  • Illustrer la protection de la branche main
  • Automatiser le déploiement en staging sur AWS EC2

User API (contexte rapide)

  • Node.js + Express, base SQLite
  • CRUD sur /api/users (GET, POST, PUT, DELETE)
  • Validation simple des champs et gestion des erreurs 400/404
  • API surtout utilisée ici comme support pour la démonstration CI/CD

Vue d’ensemble du pipeline CI/CD

dev → feature branch → PR → CI (lint + tests + coverage) → merge main → CI (lint + tests + build + deploy)
  • Workflow GitHub Actions : CI - Lint, Test, Build, Deploy
  • Jobs séquentiels : lint → test → build → deploy
  • Déploiement auto en staging sur une instance AWS EC2

Qualité : ESLint + Jest + couverture

Linting

  • ESLint v10, flat config (eslint.config.cjs)
  • Script : npm run lint
  • Job CI lint échoue si des erreurs sont détectées

Tests

  • Jest + Supertest (tests d’intégration HTTP)
  • Script : npm test (avec --coverage)
  • Tests couvrant succès + erreurs (400, 404, email dupliqué…)

Couverture ≥ 70 %

  • coverageThreshold global défini dans package.json
  • Branches, fonctions, lignes, statements ≥ 70 %
  • Si la couverture descend < 70 % :
    • npm test échoue → job test rouge
    • La PR ne peut pas être mergée sur main
    • Le déploiement est bloqué

Workflow GitHub Actions

.github/workflows/ci.yml

lint  →  test  →  build  →  deploy (staging EC2)
  • lint : installe les dépendances, exécute ESLint
  • test : dépend de lint, exécute Jest + coverage
  • build : dépend de test, prépare l’étape de build
  • deploy : dépend de build, déploie sur AWS EC2 (staging)

Garde-fous de merge sur main

  • Branche main protégée : pas de git push origin main direct
  • Merge uniquement via Pull Request
  • Règle GitHub :
    • Require a pull request before merging
    • Require status checks to pass before merging
    • Checks requis : jobs lint, test, build
  • Conséquence : aucune branche ne peut être mergée si :
    • ESLint trouve des erreurs
    • La couverture globale < 70 %

Déploiement staging sur AWS EC2

Architecture simple

  • EC2 Ubuntu (staging)
  • Node 20, npm, PM2 installés
  • App clonée dans /var/www/user-api
  • Process PM2 user-api redémarré à chaque déploiement

Sécurité & réseau

  • Security Group : SSH 22, port API 3000 ou HTTP/HTTPS
  • Durcissement SSH : clés, PasswordAuthentication no
  • Pare-feu UFW en complément (ports min nécessaires)

Job deploy : détail

  • Déclenché uniquement sur push sur main/master après build OK
  • Action appleboy/ssh-action pour exécuter des commandes à distance
  • Secrets GitHub :
    • AWS_EC2_STAGING_HOST
    • AWS_EC2_STAGING_USER
    • AWS_EC2_STAGING_SSH_KEY
    • AWS_EC2_STAGING_SSH_PORT
    • AWS_EC2_STAGING_APP_DIR
  • Script distant :
    • cd $AWS_EC2_STAGING_APP_DIR
    • git fetch + git checkout main + git pull
    • npm ci --omit=dev
    • pm2 reload user-api ou pm2 start src/server.js --name user-api

Bénéfices du pipeline CI/CD

Fiabilité garantie

Le code en staging/prod a toujours passé lint et tests avec une couverture globale ≥ 70 %.

Automatisation totale

Du commit au déploiement sur EC2, tout est automatisé via GitHub Actions, sans intervention manuelle.

Sécurité des déploiements

Protection de branche + checks obligatoires empêchent les merges de mauvaise qualité et les déploiements cassés.

Résultat : un workflow DevOps robuste qui assure qualité, sécurité et rapidité de déploiement.

Conclusion

  • Petit projet, mais pipeline CI/CD complet et robuste
  • Facile à étendre vers la prod (load balancer, Docker, etc.)
  • Base solide pour discuter de bonnes pratiques DevOps
